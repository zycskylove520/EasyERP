# 业务变更 02 · 品类规格字段变更的连锁影响（已实现，主人同意推荐方案）

> 实现：quotation_items 加 spec_labels JSON（制单时存 key→label 快照）；getPrintData 的 labelOf 优先用快照、无快照才回退查品类schema、再回退 key。前端制单/编辑随 specs 提交 specLabels。新增 2 个测试验证「改品类 label 后历史报价单仍用旧 label、新单用新 label」。29 测试通过，真实库迁移实测生效。

> 主人问：「如果产品品类里用户修改了某个品类的规格字段，那么应该同时调整货品管理，而报价单这一块你认为如何处理比较好？」

## 1. 现状数据模型
- 品类规格模板：`product_categories.spec_schema`（字段 key/label/type/unit）
- 货品规格值：`products.specs`（key→值），**活数据**，归属某品类
- 报价明细规格值：`quotation_items.specs`（key→值），**制单时的独立快照**，不引用货品

## 2. 现有保护（已实现）
`CategoryService.update` 的 `assertNoFieldLost`：若某规格字段已被该品类货品使用（specs 里有该 key），则**禁止删除/改名**该字段（409）。所以货品数据目前是安全的。

## 3. 三种变更场景与影响
| 场景 | 货品管理 | 报价单 |
|---|---|---|
| **新增字段** | 老货品没有该 key，显示 '-'，编辑可补填；无破坏 | 新制单自动用新字段；老单据快照不受影响 |
| **改 label/单位**（不改 key） | 列表列头自动变中文新 label（前端按 schema 映射），值不变 | 老单据打印时按当前 schema 取 label——可能"历史单据表头变了" |
| **删/改 key（已被使用）** | 现有逻辑已禁止 | 老单据快照仍保留旧 key（数据不丢） |

## 4. 我的建议（推荐方案）

**核心原则：货品是"活数据"跟着品类 schema 走；报价单是"历史快照"不跟着变。**

- **货品管理**：已经跟着 schema 走（动态列 + 中文 label 映射，新增字段显示 '-'）。无需大改，只需确认：改 label 后列表列头自动更新（已实现）。
- **报价单**：
  - **历史单据**：规格快照保持制单时的原样，**不随品类 schema 变化**——这是会计/单据的正确语义（单据是当时的事实）。
  - **新制单**：自动用最新 schema。
  - 实现上：打印数据的 label 映射**改为存进明细自身的快照**（制单时把 label 一起存），而不是打印时现查品类 schema。这样老单据表头永远是最初的 label。
- 变更约束沿用现有：被货品使用的字段禁止删/改 key（保护活数据）；报价明细快照不因此受限。

## 5. 备选（若主人要"报价单也跟着变"）
- 打印时按当前 schema 现查 label（即现状），老单据列头会跟着品类变——**不推荐**（篡改历史单据语义），但实现最简单。
