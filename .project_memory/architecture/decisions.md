# 架构层 · 关键决策记录

> 每条决策写清「是什么 + 为什么 + 取舍」，带日期与证据。旧决策被取代时标注日期与原因，保留原文。

## D-001 · 采用 pnpm workspace monorepo（2026-11-21）
- 是什么：单仓多包，`apps/api` + `apps/web`，根 `package.json` 设 `private: true`。
- 为什么：前后端同仓，便于统一版本、共享配置、未来抽公共类型包；主人在 Node 生态下选了 NestJS + Vue3。
- 取舍：比两个独立仓库多一点 workspace 配置复杂度，换来协作与共享便利。
- 证据：主人 2026-11-21 选择「从零新建 / NestJS / Vue3+Vite」。

## D-002 · 首版只搭骨架、不预置业务模块（2026-11-21）
- 是什么：只建可运行的 api/web 最小工程 + 依赖，业务模块留空。
- 为什么：主人明确「先安装依赖，晚点告诉需要哪些功能」；避免凭空臆造业务类型。
- 取舍：交付时系统无实际业务功能，需后续按需求迭代。
- 证据：主人原话 2026-11-21。

## D-004 · 库存用流水账模型，支持制单扣减/打回冲销（2026-11-21）
- 是什么：`inventory_ledger` 流水表，当前库存 = 流水 delta 之和；制单确认写负流水，打回/回撤写正流水冲销（`reversal_of` 指回原流水，防重复）。
- 为什么：主人明确「库存台账，制单后自动扣减，但要支持打回和回撤」。只存可变数量无法追溯，流水账天然可审计、可扩展。
- 取舍：查询当前库存需 SUM，比直接读数字略慢；换来完整账目与可回溯。
- 证据：主人反馈 2026-11-21 第 1 条。

## D-005 · 数据库选 better-sqlite3 + 轻量封装，不用 TypeORM（2026-11-21）
- 是什么：单文件 `apps/api/data/easyerp.db`，同步 API + 原生事务；不用 ORM，直接写 SQL 封装。
- 为什么：主人要轻量、可移植、内置、随软件走；库存冲销必须靠事务保证一致性。实测项目内 Node 22.23.5 装得上（prebuild-install 拉到预编译包，CRUD 通过）。
- 取舍：原生模块需一次性补装二进制（流程记在 `.tools/README.md`）；换来零外部服务与完整事务。
- 证据：主人反馈 2026-11-21 第 2、3 条 + 本机实测。

## D-006 · 规格用 JSON + 品类 spec_schema，预留扩展字段（2026-11-21）
- 是什么：`product_category.spec_schema` 描述字段，`product.specs` 存值；预置 color/克重/备注等 reserved 字段。
- 为什么：6 类货品规格字段不同，且主人要求「预留后续增加字段」。
- 取舍：JSON 不如关系列好做复杂查询；换来自由扩展、不动表结构。
- 证据：主人反馈 2026-11-21 第 2 条。

## D-003 · 语言统一 TypeScript + strict（2026-11-21）
- 是什么：前后端均 TS，开启 `strict`，禁用 `any`。
- 为什么：engineering-craft TS 语言规范基线；ERP 业务数据形状复杂，强类型降低错误。
- 取舍：比 JS 多写类型，换取可维护性与边界校验。
- 证据：engineering-craft `languages/typescript.md`。
